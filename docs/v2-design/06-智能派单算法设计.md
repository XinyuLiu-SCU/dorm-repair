# 06 智能派单算法设计（R2）

交付V2.2；V2.1提前建设预约必需的最小技能、班次、请假、工时及楼间通行配置，不提前实现完整推荐。保持可解释规则排序、管理员最终决策；不以模型打分掩盖硬约束。

## 1. 输入模型与数据来源

|输入|权威来源|缺失处理|
|---|---|---|
|项目/技能|repair_category最多三级、repairer_skill与显式scope|SELF只本项目，SUBTREE明确配置才覆盖子类；无登记排除|
|期望时间|order_time_preference版本，WINDOW或ANY|旧单UNKNOWN不当ANY；ANY在可查日期范围寻找可行时段|
|工时|类别default_duration_minutes→工单估时快照→人工调整history|缺少正工时需管理员/维修者人工填并写原因，不确认无时长预约|
|通行|building_travel_time有向分钟矩阵+楼层缓冲|未知不是0；仅展示低置信候选，人工补全后才能承诺预约|
|人员可用性|启用账号/实时权限/班次/批准请假/ACTIVE预约|缺班次不能假设全天空闲|
|资源/授权|当前preparation epoch、材料需求、有人在场或合法授权|材料未齐可推荐未来时段但不得开始维修；权限与校方入室规则另行严格校验|

学生可选ANY；WINDOW外提议不是算法自动越权扩窗，必须该提议对应学生同意后由维修者确认。已约与请假冲突走改期协商，不静默释放原预约。

## 2. 硬约束与可行区间

1. 用户/技能/资格有效，时段位于班次内。
2. 取班次减批准请假、有效预约及前后路程缓冲，与WINDOW相交；ANY在有界搜索日期内取空闲段。
3. 本次预计工时以及前预约地点→本单→后预约地点路程均可容纳，使用半开区间[start,end)；不能只算从常驻楼出发距离。
4. 所需到场/授权条件满足才允许开始；学生有意愿不代表有合法入室权。
5. 推荐不预留日历，确认时锁order→人员重验并创建预约排他预订；并行材料分支不会自行延长预约。

若准备汇合时预约过时/工时变更，结束旧epoch并整体重新准备；不能因为资源曾READY就对新材料版本继续放行。

## 3. 可复现评分

score=w_load*loadScore+w_travel*travelScore+w_time*timeScore，权重非负且和1。候选试验0.4/0.3/0.3、Top3或Top5，尚未批准具体权重。

- loadScore=1-min(1,已承诺工作分钟/可用班次分钟)，分母<=0排除。
- travelScore=1-min(1,前后增量通行分钟/Dmax)，Dmax配置版本化，不用未知位置当零路程。
- WINDOW timeScore=1-min(1,(可开始时刻-窗口起点)/窗口长度)。ANY以查询起点到搜索末端作为归一化区间，同时明确“学生时间不限”，不伪造学生偏好。

硬约束先筛，缺数据候选单列；合格候选按分数降序，再按最早可开始/有效负载/人员ID稳定排序。不要用主观差评直接惩罚无足够样本的维修者。快照保存输入order/estimate/travel/skill/rule版本、分量和reasonCodes，不存多余联系人。

## 4. 算法伪代码与复杂度

```text
批量加载窗口内人员/技能/班次/请假/预约/通行配置
for 每个人员:
    检查账号、技能与班次
    计算带路程的空闲区间
    WINDOW求交，ANY保留有界可用段
    取可容纳预计工时的候选；缺数据单列原因
    计算分量/置信度/解释
稳定排序返回TopK，不创建预订
管理员选择 -> 派单事务重验
维修人员确认具体预约 -> 再锁人员和工单、重验并预订
```

R人、每人K段，约O(R*K log K)；批量读取避免N+1，搜索日期/候选数量均有上限。建议未来一周作为待评审默认范围，不把无穷日期扫描交给用户。

## 5. 验收矩阵

|场景|预期|
|---|---|
|父类技能SELF/显式SUBTREE|前者不覆盖子类，后者覆盖且配置失效即时生效|
|WINDOW外改期/ANY|前者必须本次学生同意，后者维修者确认并通知|
|请假冲突/已有预约|不违规派单，原预约保留到改期成功|
|工时人工增大/通行配置变化|原推荐提交重验409；重新计算候选|
|并行材料迟到|汇合复核预约有效，不悄悄延时|
|两管理员/两预约抢时间|一方成功，另一方409，无重复预订|
|无技能/缺位置/缺工时/无候选|明确NO_SKILL/DATA_INCOMPLETE/NO_SLOT等原因，不伪造最佳人选|

GiST排他约束可后续增强，当前设计人员行锁协议不需要新增extension；采用extension需单独授权演练。
