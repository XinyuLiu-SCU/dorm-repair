# 04 数据库数据字典（R2）

本文件是V2逻辑设计，不是已实现字段或可执行SQL。以现有sys_user、repair_order、repair_record为增量基础，数据库变更逐阶段单独评审。09定义迁移与历史保护规则。

## 通用约定

新增主键bigint identity；API V2把ID编码为十进制字符串，避免JavaScript精度损失。业务展示金额2位；库存价值numeric(18,4)、单位成本numeric(18,6)、数量numeric(12,3)，禁止浮点金额；库存精度以本轮增量节为准。新增时间timestamptz，区间为[start,end)，check start < end；已有timestamp未经时区核验不自动转换。可变聚合有version integer not null default 0。created_at默认当前时间；updated_at由应用统一设置。状态使用varchar加check，枚举更改需版本迁移。下表所有必填业务关联均使用外键，历史引用on delete restrict；停用替代删除。

密码哈希沿用BCrypt，不在任何查询DTO返回。电话号码属于私密信息。常用查询索引末尾追加id保持稳定排序。除明确可空项外，标识、状态、业务必需字段均not null；可选说明/尚未发生时间可以为空。图片每组6张/单张5MiB，JPG/PNG/WebP；分类根算第1级、最多三级；验收7天/评价15天。规则以01 BR01–BR12为准。

## 事务和一致性落点

- 工单命令：锁order，检查版本/身份/合法节点，写业务与Flowable、记录、审计、Outbox；任何失败整体回滚。同一DataSource/事务管理器沿用V1验证。
- 预约：先order后按ID排序锁涉及的repairer用户行，重验排班/请假/预约区间；释放旧预订、确认新预订、更新Flowable同事务。请假操作锁人员行后发现已有预约返回冲突，不逆向锁工单。
- 库存：order→人员（若涉及）→按item_id升序锁stock_balance；申请批准增加reserved，发料同时减少on_hand/reserved并写唯一流水和usage；不足返回409，不出现负库存。通知不在事务内调用外网。
- 默认地址：锁sys_user行，取消旧默认再设新默认，部分唯一索引兜底。
- 定时巡检：唯一(plan_id,scheduled_at)兜底，SKIP LOCKED领取到期计划；异常转单有唯一finding关联，失败不留下半个流程。
- Outbox至少一次投递；消费事件键唯一去重，失败不能静默标成功。SQL分页和批量关联取数，避免N+1。

所有JSON仅用于推荐快照/脱敏事件，不把可关联核心业务藏在无约束JSON。正式DDL、索引执行计划和数据回填脚本在对应开发阶段再产出、测试、授权。

权限变更事务统一锁定授权管理哨兵行（或明确的同一管理聚合锁），按用户ID顺序更新受影响用户auth_version，防止两个管理员并发互相停用后无可用管理者。角色权限更新、最后管理者检查及会话失效必须原子完成；哨兵存于单行system_guard表（guard_key主键，version），不引入外部锁服务。

## 位置/资料/分支的跨表约束落点

- room提供unique(id,building_id)，facility提供unique(id,building_id,room_id)等可引用键；地址/快照的(room_id,building_id)组合FK保证同楼。公共位置room为空时check要求public_zone，不能依赖NULL复合FK自动验证所有分支。
- 私密设施关联工单时，Service在锁设施/工单所需的统一顺序下核对该版本快照位置；若选facility则默认使用其真实位置，拒绝矛盾address输入400，禁止“校正”成别人的宿舍。设施移动后历史快照不变，记录facility_location_version用于审计。
- active_revision_id、current_cycle_id、active_preparation_id通过包含order_id的组合外键保证同单；快照/修订循环引用创建时可延后约束至事务提交或先插快照再修订最后切active，DDL阶段选定一种并演练。
- 图片数量/资料版本/轮次递增、无窗口外同意不能确认预约等跨行规则在工单行锁事务内校验；check不假装能跨表表达。数据库唯一和FK兜底，触发器只在确有必要时另议。
- process_link域引用落实为显式order_id/material_request_id/complaint_id/followup_id/inspection_batch_id列及“恰一主域”check；表中domain_type/domain_id是API投影，不保留不能FK验证的自由多态主引用。ROOT/MATERIAL的order_id是作用域附属关联，不纳入恰一主域计数。

## 库存成本与退料事务（候选技术口径）

入库移动均价=(原库存价值+本次入库价值)/(原数量+入库数量)；实发冻结该时点单位成本，退料按原出库单位成本还原，不按今日采购价。每次修改统一锁order→申请→相关人员→按item排序库存；退料锁涉及原流水按ID顺序，不反向锁工单。重试使用唯一幂等键，冲正追加相反流水且累计校验，不直接删除库存账。已发到原维修者的材料转派必须有实物交接/退料记录；没有确认不得把holder_id改成新维修者。

正式财务计价未确认前保留这份候选口径及精度，不提前出具“已核准成本报表”。库存为0时残余价值如何归零需明确受审计尾差调整。

### 外键、交接与投影字段最终核对

- repair_cycle、preparation_cycle、repair_appointment均带order_id并提供unique(id,order_id)；preparation_cycle额外FK(cycle_id,order_id)→repair_cycle，其他当前指针用组合FK保持同单。cycle/epoch编号唯一不能替代同单约束。
- repair_order.hold_reason可空，TRANSFER_MATERIAL_SETTLEMENT等受控值由命令写入；orderHold是DTO投影，不由客户端自行清除。准备/暂停/公共状态由05聚合规则映射。
- material_handover：id、request_id、original_issue_movement_id、from_holder_id、to_holder_id、qty>0、status、confirmed_from_by/at、confirmed_to_by/at、idempotency_key唯一。真实FK，累计交接量不能超过该持有者尚持有原批次数量；双确认或批准的仓库接收才生效。只改变实物保管责任，不重复扣库存/记录成本，退料仍用原出库冲正。
- 库存每次入库/原价退料后以(更新后inventory_value/on_hand)重新派生moving_avg_cost；实发成本快照不变；库存归零的价值尾差按受审计调整，不修改旧流水。
- /workflow/task-counts分别返回taskTotal与distinctOrderTotal，不能把多任务数量误叫工单数；统计权限与列表筛选相同。
