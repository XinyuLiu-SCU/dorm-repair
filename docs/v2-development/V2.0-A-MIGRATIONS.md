# V2.0-A 迁移机制与兼容性

## 选择与边界

使用Boot3.5.16管理的Flyway11.7.2 + flyway-database-postgresql，实测PostgreSQL17.6。Flyway负责**新增业务版本**的执行和校验和，不接管Flowable内部act_/flw_表；原backend/deployment/postgres-flowable-7.2.0及D001账保留独立含义。不引入Hibernate自动建表，不将候选BPMN放入自动扫描目录。

官方参考：[Boot3.5 Flyway属性](https://docs.spring.io/spring-boot/3.5/appendix/application-properties/)、[Flyway baseline-on-migrate风险](https://documentation.red-gate.com/flyway/reference/configuration/flyway-namespace/flyway-baseline-on-migrate-setting)。默认baseline-on-migrate=false；本项目也禁止自动clean或repair。版本选择以本地依赖树和运行测试为准。

## 两条显式版本迁移

|版本|实际动作|不做什么|
|---|---|---|
|V1 verify_or_bootstrap_v1_core|空库创建兼容V1的sys_user/repair_order/repair_record；已有库先通过Java只读结构核验，再记录本次真实验证/建表脚本执行|不reset用户或密码，不插默认用户；不是baseline跳过未执行脚本|
|V2 prepare_legacy_workflow_association|追加可空process_instance_id、部分唯一索引、legacy登记；已有合法关联结构验证后保持；只登记当前无实例的存量行|不启动流程、不创建引擎表、不为历史单补实例|

没有创建任何动态RBAC、分类/地址/图片等V2业务表。SQL不可变，后续B从V3及更高版本追加，不编辑已应用脚本来“修复”校验和。

## 为什么history单独放schema

v2_business_history.flyway_schema_history是新的业务迁移账，脚本中的业务对象明确public前缀。Flyway schemas只声明自己的history schema，不将引擎或整个public视为可清理托管对象；clean始终禁用。非空public不触发盲baseline：在任何Flyway migrate前，LegacySchemaVerifier检查三表完整性、精确列/类型/长度/空值、identity/default、PK/username唯一、四个FK、安全枚举和已有关联/legacy登记。

只支持“空public”或已核对的V1结构；部分/漂移/未知结构拒绝，必须人工调查。接管是V1脚本真正执行时对已存在对象no-op，并记录该版本，不是声称曾跑过过去的D001或其他未知脚本。已有迁移账时Flyway validate校验历史与SQL，不声称它可以发现任意手工DDL漂移；后续可增加独立schema审计。

## 保护检查顺序

1. V2环境DEV/TEST、固定本机URL、指定v2_dev/v2_test名、127绑定和18081或测试0端口；禁止URL参数和远程主机。
2. Flowable/自动DDL/async executor/workflow全部false。禁止独立spring.flyway.url/user/password，Flyway必须为同一个应用DataSource。
3. baseline=false、cleanDisabled=true、validate=true、group=true、mixed=false，history schema准确。
4. 实际连接URL/catalog/产品名复核；只读验证V1结构；然后才migrate。每份SQL另有current_database名称保护。
5. 默认/原integration配置Flyway关闭；即使误设spring.flyway.enabled=true，非V2环境的拒绝策略也会在migrate前终止，不能自动给正式库建history。

这是防误操作，不替代数据库最小权限。数据库管理员可绕过代码执行SQL，不能把任何脚本当作正式迁移授权。

## 事务失败与恢复

PostgreSQL DDL可事务化；group=true把当前所有待执行SQL置于同一迁移事务，mixed=false不混入非事务操作。故障注入V3创建临时业务表后除零，实测V1/V2/故障业务DDL全部回滚，history不记录成功版本。Flyway创建的history schema/表可能保留为空或仅有schema创建记录，这是**已声明的元数据**，不是半完成业务结构。

失败时先查原因，修正未发布的错误脚本或追加合法前滚；不自动baseline/clean/repair，不因失败删数据重跑。未来CONCURRENTLY索引等非事务迁移须另评执行机制，不能直接放入此group流程。

## 测试边界

专用V2测试库验证空库、模拟V1、已有关联与32张引擎表、重复迁移、漂移拒绝、事务回滚和checksum不匹配。原66项回归改为可选测试库和随机HTTP端口，断言未降级。初始化工具只创建固定隔离名；重置逻辑只在测试源中，限定两个测试目标并复核catalog，禁止dev/正式/旧联调。

正式库尚未迁移，不对其执行这些脚本。今后正式接管仍需另行导出结构、核验指纹、备份演练和授权，不能以本轮隔离验证代替。
