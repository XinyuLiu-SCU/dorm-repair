# V6分情况授权修正与受控迁移

旧草稿已隔离，禁止执行；新V6__guarded_catalog_grants.sql不改V1–V5。

## 空用户库

锁rbac-admin后检查用户、初始化标记、角色集合及授权模板。存在自定义角色、未知身份权限或初始化标记则拒绝，避免以“没人登录”为由覆盖合法自定义配置。只在可核验三个种子模板时规范三个catalog写权限：ADMIN拥有全部有效权限，STUDENT/REPAIRER不拥有管理写权限。无密码、无账户创建。

## 已执行V4且有用户

没有迁移前授权来源快照，不能自动判断V4扩散和后续合法授权。默认必须失败，在任何授权写入前抛错。受信运维操作者若有可信快照/审计历史或经确认的完整授权映射，才可在Flyway同一数据库连接中提供临时表pg_temp.c6_confirmed_grants(role_id bigint,permission_code varchar(80),主键二者)。它明确给出三个catalog写权限的完整期望角色集合，不能只写增量。

这是本地DB运维边界，不是HTTP参数或允许前端提交的权限恢复接口。应用默认profile没有配置自动提供映射，不把任意JSON称作可信证据。未知角色/权限拒绝；映射若失去最后有效全权保管人则整个迁移回滚。其他权限点和用户角色关联不变；仅依据明确映射调整三个catalog写权限，受影响用户auth_version/version增加以撤销旧Token。

不要用“当前ADMIN名称”“最小用户ID”“当前所有全权者”推断迁移前合法全权。可建立专用补充角色，但角色ID及关联同样必须来自确认方案；本迁移不会猜测并创建保管人。

## 未来非空V3库升级

1. 受控维护窗口停止该V2服务，核对进程归属；不触碰8080/18080。
2. 在V4前导出脱敏授权快照：用户ID/启用/auth_version/version、角色ID/启用/version、用户角色关系、角色权限关系及Flyway版本/校验和。禁止导出密码哈希、联系人或Token；快照存于Git忽略目录，记录校验摘要。
3. 按该快照明确合法全权用户；如其通过共享角色取得权限，确认建立独立补充授权角色及关联，避免把新增写权限放到普通共享角色。由操作者审核V6完整映射，包含后来合法授权，不能机械回滚至旧权限集合。
4. 同一受控Flyway连接通过初始化SQL加载已审核临时映射，保持group=true，V4/V5/V6在一个迁移事务内完成；默认启动先迁移后开放HTTP。V6缺映射则整组回滚，不能只启动到V4向业务暴露临时权限。
5. 提交后校验有效权限集合、用户关联、版本、最后保管人及旧Token401，再开放该V2服务。快照生成、人工映射审核和审批均为运维操作，不实现任意历史授权自动恢复系统。

本轮自动化真实PostgreSQL覆盖无证据拒绝、明确映射修复共享扩散、合法有限授权保留、最后保管人保护、事务回滚与重复启动；真实HTTP覆盖迁移后旧Token401和新Token403/管理恢复。
